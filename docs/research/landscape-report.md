# Scaffold agent memory once, read it everywhere

The tool you are describing sits in an **unclaimed niche**: a safe, repeatable CLI that scaffolds human-readable markdown memory for *both* a personal knowledge vault and the many code repos a developer works in, wired to every major agent through open standards rather than per-vendor adapters. The category has no settled name; the right vocabulary is to lead with the patterns people already search for ("LLM wiki", "AI second brain") and describe the mechanism as "context engineering in plain markdown", while avoiding "agent memory layer", which signals a database/API product like Mem0 or Zep. To stay AI-agnostic, build on three cross-vendor standards: **AGENTS.md** (Linux Foundation-stewarded and natively read by nearly every coding agent in 2026), **Agent Skills / SKILL.md** (40+ clients), and **MCP** (the settled tool transport), with CLAUDE.md, GEMINI.md and the rest generated as thin bridges. Graphify is a hugely popular (~128k stars) corpus-to-knowledge-graph indexer, not a memory store, so it belongs in an optional, rebuildable layer; Obsidian should be the recommended viewer, never a runtime dependency. The prior art is crowded on vault templates and spec-driven toolkits but nothing unifies vault plus repos, agent-neutrality by construction, safe bootstrap/upgrade, and built-in freshness. Finally, **"mindpalace" is a real liability as a public name**: MemPalace, a viral April 2026 open-source "memory palace" AI memory project, owns the same metaphor in the same domain, so keep mindpalace as the working folder and ship under a different name.

## "Context engineering" is the discipline; "LLM wiki" is the searchable pattern

No single label has won. "Context engineering" is the umbrella discipline term, defined by Anthropic as "the set of strategies for curating and maintaining the optimal set of tokens" at inference time ([Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)) and used in parallel by Manus ([Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)) and OpenAI's cookbook ([OpenAI Cookbook](https://developers.openai.com/cookbook/examples/agents_sdk/context_personalization)). "Agent memory layer" is the established product category, but it denotes services like Mem0, Letta, Zep and Cognee, which are "not interchangeable" with each other let alone with a scaffolder ([Developers Digest](https://www.developersdigest.tech/blog/best-ai-agent-memory-providers-2026)). Using that label would invite the wrong comparison.

The momentum term for file-based, agent-maintained knowledge is the **LLM Wiki**, from Andrej Karpathy's April 4, 2026 gist: immutable raw sources, an LLM-maintained interlinked markdown wiki, and a schema file (CLAUDE.md/AGENTS.md), operated through ingest, query and lint, with `index.md` and an append-only `log.md` as the special files. Its framing, "Obsidian is the IDE, the LLM is the programmer, the wiki is the codebase", and its claim that an index file suffices to roughly 100 sources before you need a search tool, define the current design default ([Karpathy gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)). Press immediately conflated it with "second brain" ([Medium/NeuralNotions](https://medium.com/neuralnotions/andrej-karpathy-stopped-using-ai-to-write-code-hes-using-it-to-build-a-second-brain-instead-cddceadc5df5)), and an active Obsidian-plus-Claude-Code "AI second brain" scene has formed around it ([HackerNoon](https://hackernoon.com/obsidian-holds-the-notes-claude-does-the-work-second-brain)). The older "memory bank" term is Cline-specific: a fixed `memory-bank/` folder of six files bootstrapped by a `.clinerules` instruction ([Cline docs](https://docs.cline.bot/prompting/cline-memory-bank)).

For internal design, the vocabulary to adopt is the cognitive split LangMem popularized: semantic (facts, stored as an editable "profile" or a growing "collection"), episodic (past experiences and summaries) and procedural (behavior rules) ([LangMem](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)). It maps cleanly onto files: semantic memory is wiki and profile pages, episodic memory is `log.md` and session journals, procedural memory is AGENTS.md plus SKILL.md, and working memory is a scratch/todo file. Anthropic's own memory tool takes the same minimalist stance, a `/memories` directory the model reads before work and edits with plain file commands, paired with compaction because "memory preserves the information that must survive summarization" ([Claude docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)). Even Letta, the archetypal memory-runtime vendor, moved its Letta Code memory to a git-backed directory of markdown files in February 2026 ([Letta](https://www.letta.com/blog/context-repositories)). The industry is converging on exactly the substrate a bootstrapper produces.

The practices experts agree on translate directly into scaffold features: keep the always-loaded file small because recall degrades as context fills; load deeper files just-in-time via paths and links ([Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)); keep the prompt prefix stable and append-only, since Manus calls KV-cache hit rate "the single most important metric" ([Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)); and run background consolidation passes, Letta's "sleep-time compute" being the canonical example ([Letta](https://www.letta.com/blog/sleep-time-compute)). The risk side is equally clear: memory poisoning is a named OWASP agentic risk (ASI06), a persistent prompt injection that survives sessions ([Kiteworks](https://www.kiteworks.com/cybersecurity-risk-management/owasp-agent-memory-poisoning-guard/)), and Anthropic recommends stripping sensitive data before writes, path-traversal checks, size caps and expiring stale files ([Claude docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)).

## Graphify indexes a corpus into a graph; it does not remember

**Graphify** is a Python CLI plus agent skill, now under the Graphify-Labs organization (originally `safishamsi/graphify`), with roughly **127.9k stars** and active releases. It turns a folder of code, docs, SQL schemas, PDFs and images into a queryable knowledge graph ([GitHub](https://github.com/safishamsi/graphify)). Code is parsed deterministically with tree-sitter across 40+ languages at zero LLM cost; docs, papers and images go through an LLM "semantic pass" using the host agent's model; Leiden community detection finds clusters and "god nodes"; and every edge is tagged EXTRACTED, INFERRED or AMBIGUOUS. Outputs are files, not a database: `graph.json`, an interactive `graph.html`, a `GRAPH_REPORT.md`, and optional `obsidian/` vault and `wiki/` exports, with a SHA256 cache for incremental rebuilds and an `--mcp` stdio server ([README](https://cdn.jsdelivr.net/gh/safishamsi/graphify@main/README.md)). It installs into 20+ agents, from Claude Code and Codex to Cursor, Gemini CLI, Copilot, Aider and OpenCode ([GitHub](https://github.com/safishamsi/graphify)).

Its caveats matter for a project that promises neutrality and local-first behavior. The headline **"71.5x fewer tokens"** comes from a 52-file corpus; the README concedes about **1x** on a 6-file library, so small personal projects gain structure but not compression ([README](https://cdn.jsdelivr.net/gh/safishamsi/graphify@main/README.md)). The license is unresolved, with both Apache-2.0 and MIT files shown on GitHub and third parties disagreeing, and the README promotes a paid "Graphify Cloud" tier, an open-core signal ([GitHub](https://github.com/safishamsi/graphify)). Queries are logged to `~/.cache/graphify-queries.log` by default, non-code content is sent to the LLM despite "runs locally" framing, inferred edges need verification ([GitTrend](https://gittrend.io/repo/Graphify-Labs/graphify)), and the Claude Code install writes into `~/.claude/CLAUDE.md` and adds PreToolUse hooks ([augmentcode](https://www.augmentcode.com/learn/graphify-knowledge-graph-codebase-skill)). Its Obsidian export appears to be one-way, so edits in Obsidian do not flow back into `graph.json`. No independent benchmark of its savings exists; its own LOCOMO comparison (45.3% vs supermemory's 49.7%) measures conversational memory, which graphify is not designed for.

The alternatives split along one axis that matters most for your design: does the human-readable markdown stay the source of truth?

| Tool | Store of record | Human-readable / Obsidian | MCP | License | Fit for this project |
|---|---|---|---|---|---|
| graphify | graph.json + exports | Export only, one-way | Yes | Apache-2.0/MIT unclear | Optional derived index for code/large corpora |
| Basic Memory | Markdown + SQLite index | Yes, same folder | Core | AGPL-3.0 | Best optional runtime MCP over the vault |
| Letta Code MemFS | Markdown in git | Yes | Letta-specific | Apache-2.0 | Validates the design; not reusable |
| Graphiti / Zep | Neo4j/FalkorDB/Neptune | No | Yes | Apache-2.0 | Plug-in for temporal conversational memory |
| Cognee | Graph + vector + relational | No | Yes | Apache-2.0 | Plug-in; keyless local mode |
| Mem0 / OpenMemory | Qdrant + Postgres | No | Yes | Apache-2.0 | Out of scope (runtime service) |
| MCP reference memory | Single JSONL | Readable, not Obsidian | Yes | MIT | Too thin |

Sources: Basic Memory ([GitHub](https://github.com/basicmachines-co/basic-memory)), Letta MemFS ([docs](https://docs.letta.com/letta-code/memfs)), Graphiti ([GitHub](https://github.com/getzep/graphiti)), Cognee ([GitHub](https://github.com/topoteretes/cognee)), Mem0 ([GitHub](https://github.com/mem0ai/mem0)), OpenMemory ([Mem0 blog](https://mem0.ai/blog/introducing-openmemory-mcp)), MCP memory server ([GitHub](https://github.com/modelcontextprotocol/servers/tree/main/src/memory)).

Graph databases win on multi-hop and temporal queries (Graphiti's bi-temporal fact invalidation is genuinely powerful), but they cost LLM extraction, add infrastructure, and degrade with small local models that emit schema-mismatched JSON ([Graphiti](https://github.com/getzep/graphiti)); Microsoft's GraphRAG warns its indexing is "an expensive operation" and is now in maintenance mode ([GraphRAG](https://github.com/microsoft/graphrag)). Practitioners on HN note that an MCP memory server often performs "about the same as grep in a memory/ directory" at personal scale, while an index starts paying off at hundreds of notes ([HN](https://hn.svelte.dev/item/49286073)). The emerging consensus, which the evidence supports, is **markdown as truth plus rebuildable derived indexes**. Obsidian's wikilink graph is already a lightweight, human-curated knowledge graph; an LLM-extracted graph adds breadth at the cost of trust.

## AGENTS.md, Agent Skills and MCP are the only neutral ground

**AGENTS.md** is the closest thing to a universal instruction file. It is stewarded by the Agentic AI Foundation, a Linux Foundation directed fund formed on December 9, 2025 with MCP and goose as fellow founding projects and AWS, Anthropic, Google, Microsoft and OpenAI among platinum members ([Linux Foundation](https://linuxfoundation.org/press/linux-foundation-announces-the-formation-of-the-agentic-ai-foundation)). Its spec says the nearest file in the tree wins and chat prompts override all files ([agents.md](https://agents.md/)). In 2026 a root AGENTS.md reaches roughly 11 of 12 major tools with zero config: Codex, Cursor, Copilot, OpenCode, Amp, Windsurf, Cline, Zed and, since v2.1.277, Claude Code natively ([Claude Code docs](https://code.claude.com/docs/en/memory)). Some older third-party comparisons still say Claude Code needs a workaround ([inventivehq](https://inventivehq.com/blog/claude-md-vs-agents-md-vs-gemini-md)); the primary docs supersede them, but the workaround remains necessary in practice for a different reason (below). Gemini CLI reads only GEMINI.md unless you set `context.fileName` ([Gemini CLI docs](https://geminicli.com/docs/cli/gemini-md/)), and Aider's native behavior is disputed, so a `read:` entry in `.aider.conf.yml` is the safe bridge ([Mintlify](https://www.mintlify.com/agentsmd/agents.md/compatibility/aider)).

Four portability traps should be encoded as lint rules. First, Claude Code's default mode reads AGENTS.md **only when no CLAUDE.md exists**, so any generated CLAUDE.md must contain `@AGENTS.md`; Anthropic's docs recommend the import over a symlink because Claude's edit tools refuse to write through symlinks and Windows checks out committed symlinks as plain text ([Claude Code docs](https://code.claude.com/docs/en/memory)). Second, nesting semantics differ: Codex concatenates root-to-leaf and **caps the total at 32 KiB by default** ([Codex docs](https://learn.chatgpt.com/docs/agent-configuration/agents-md)), Copilot is nearest-wins ([GitHub Docs](https://docs.github.com/en/copilot/how-tos/configure-custom-instructions/add-repository-instructions)), and Zed reads only the first root file with no merging, so critical rules belong in the root file. Third, Zed picks `.rules`, `.cursorrules`, `.windsurfrules`, `.clinerules` or `.github/copilot-instructions.md` *before* AGENTS.md, so emitting any legacy root file silently shadows the canonical one ([Zed commit](https://git.secluded.site/zed/commit/12bdc208e5298a6aaa1803b07bf6f63599cb6add)). Fourth, path-scoped rules have no common format (Cursor `globs` in `.mdc` files, Copilot `applyTo`, Cline `paths`), so they require generation ([Cursor docs](https://cursor.com/docs/context/rules); [Cline docs](https://docs.cline.bot/features/cline-rules)).

**Agent Skills** is the procedural-memory standard: a folder with a `SKILL.md` whose required frontmatter is just `name` (lowercase, hyphenated, matching the folder) and `description`, loaded by progressive disclosure at about 100 tokens of metadata per skill, with bodies under 5,000 tokens ([agentskills.io spec](https://agentskills.io/specification)). More than 40 clients support it, including Claude Code, Codex, Gemini CLI, Cursor, Copilot, OpenCode, Amp, goose and Letta ([agentskills.io](https://agentskills.io/)). `.agents/skills/` is emerging as the neutral directory (Cursor reads it plus `.claude/skills/` for compatibility ([Cursor docs](https://cursor.com/docs/context/skills))), but Claude Code reads nothing under `.agents/`, so skills must be mirrored to `.claude/skills/`. Keep to required fields so every client parses them.

**MCP** is the settled cross-vendor tool layer, now under the same foundation, with a major stateless-core revision dated 2026-07-28 ([AAIF](https://aaif.io/blog?hsLang=en)). It is the only neutral way to give agents read/write memory at runtime, but its config files are vendor-specific, which is why Ruler and rulesync generate them from one canonical server list ([Ruler](https://github.com/intellectronica/ruler); [rulesync](https://github.com/dyoshikawa/rulesync)).

There is **no adopted portable memory standard**. A W3C Community Group chartered in June 2026 ([W3C](https://www.w3.org/community/ai-agent-memory-interop)) and proposals such as MacPaw's `.mem` bundle, whose authors concede it is not independently implemented ([MacPaw](https://research.macpaw.com/publications/portable-memory)), are too early to build on. Vendor memories remain siloed, such as Claude Code's auto memory in `~/.claude/projects/<project>/memory/MEMORY.md`, which loads the first 200 lines or 25 KB each session ([Claude Code docs](https://code.claude.com/docs/en/memory)). That index-plus-topic-files shape is worth copying into the repo, where every agent can read it. llms.txt is irrelevant here: it is ungoverned and AI crawlers barely consume it ([Digital Applied](https://www.digitalapplied.com/blog/llms-txt-in-practice-adoption-evidence-2026)).

## Crowded on templates, empty where vault meets repos

The Obsidian-agent space is busy. The largest projects as of October 18, 2026 are claude-obsidian (~15.6k stars), an LLM Wiki implementation with a plan-hash-approved `init`, a non-destructive `adopt`, claim ledgers and transactional writes ([claude-obsidian](https://github.com/AgriciDaniel/claude-obsidian)); the Claudian plugin (~15.7k), which embeds an agent inside Obsidian ([Claudian](https://github.com/YishenTu/claudian)); obsidian-second-brain (~4.8k), whose "timeless, dated, or pointer" rule for every stored fact is an explicit anti-staleness design ([obsidian-second-brain](https://github.com/eugeniughelbur/obsidian-second-brain)); obsidian-wiki (~3.6k), with SessionStart/SessionEnd hooks, an atomic writer for parallel agents and a source manifest for incremental ingest ([obsidian-wiki](https://github.com/Ar9av/obsidian-wiki)); claudesidian (~2.6k), a numbered PARA template with an interview-driven `/init-bootstrap` and a customization-preserving `/upgrade` ([claudesidian](https://github.com/heyitsnoah/claudesidian)); and COG (~1.3k), whose `memory-hygiene` skill stamps `last_verified` and confidence ([COG](https://github.com/huytieu/COG-second-brain)). Obsidian's CEO publishes kepano/obsidian-skills (~49.7k), agent-agnostic skills that teach agents Obsidian's markdown, Bases and JSON Canvas formats ([obsidian-skills](https://github.com/kepano/obsidian-skills)). Outside Obsidian, claude-mem (~101k) captures and compresses session activity for reinjection ([claude-mem](https://github.com/thedotmack/claude-mem)).

On the repo side, spec-driven development toolkits dwarf everything: spec-kit (~142k), OpenSpec (~72k), get-shit-done (~64k) and BMAD (~54k) install folders, templates and slash commands per repo ([spec-kit](https://github.com/github/spec-kit); [OpenSpec](https://github.com/Fission-AI/OpenSpec); [GSD](https://github.com/gsd-build/get-shit-done); [BMAD](https://github.com/bmad-code-org/BMAD-METHOD)). They organize specs and tasks, not knowledge, and they live and die with one repository. Memory banks were a 2025 pattern that has largely faded; the Roo Code bank has been dormant since May 2025 ([roo-code-memory-bank](https://github.com/GreatScottyMac/roo-code-memory-bank)). Rule-sync CLIs (Ruler ~2.9k, rulesync ~1.5k) solve fan-out to each agent's files but scaffold no structure or memory ([Ruler](https://github.com/intellectronica/ruler); [rulesync](https://github.com/dyoshikawa/rulesync)).

The shared stack is now commodity: markdown, Obsidian as viewer, an AGENTS.md/CLAUDE.md schema, skills symlinked per agent, session hooks, and an index/log pair. A new project will not stand out by doing any of those. The real gaps are structural. **No tool unifies a personal vault with many code repos**; obsidian-second-brain admits "no isolation within one vault yet" and has users point each repo at a vault via an environment variable ([obsidian-second-brain](https://github.com/eugeniughelbur/obsidian-second-brain)). **Multi-agent support is bolted on**: claude-obsidian, claudesidian, context-engineering-intro ("Claude Code is the best") and GSD are Claude-first by name or description ([context-engineering-intro](https://github.com/coleam00/context-engineering-intro)). **Safe bootstrap and upgrade exist only inside individual templates.** **Freshness is opt-in**, despite the core problem that "a stale fact surfaces with the same fluent confidence as a true one" ([Mem0](https://mem0.ai/library/agent-memory/memory-staleness)). And **privacy controls are per-project**, with cloud embeddings sending note text off-machine unless users exclude folders by hand. No generic `create-*` agent-workspace scaffolder of note turned up, though npm and PyPI were not searched exhaustively, so a small one may exist.

## The name "mindpalace" walks into MemPalace's territory

MemPalace is an MIT-licensed, local-first AI memory system launched in April 2026 by Milla Jovovich and Ben Sigman. It uses the method-of-loci metaphor directly ("wings/rooms/drawers"), stores conversations verbatim with semantic search, and integrates with Claude Code hooks and MCP; aggregators reported **~19.5k stars in its first week** and about 57k later, and its benchmark claims are contested ([Better Stack](https://betterstack.com/community/guides/ai/mempalace-ai-memory/); [Vectorize](https://vectorize.io/articles/what-is-mempalace)). "mindpalace" differs by two letters, shares the metaphor, and targets the same audience in the same year. Users will read it as a fork, clone or companion, and search results will bury it. Worse, impostor MemPalace domains have distributed malware ([Vectorize](https://vectorize.io/articles/what-is-mempalace)), so a lookalike name inherits suspicion in exactly the supply-chain-sensitive moment when someone runs your installer.

The products are also genuinely different, which is the strongest reason to rename: MemPalace is a runtime that remembers conversations; your tool scaffolds and maintains the files that any runtime reads. Keep `mindpalace` as the private working directory if you like it, but publish under a name that avoids the "mem-" prefix (Mem0, MemGPT, MemPalace, Memori are already crowded ([Eden AI](https://www.edenai.co/post/ai-agent-memory-mempalace-mem0-and-persistent-context))) and the palace/loci metaphor. Prefer a name that evokes scaffolding, foundation or a shared home for context. Before committing, check GitHub, npm and PyPI, and run a basic trademark search; the PyPI name collisions around graphify and rulesync show how common squatting is in this space.

## Recommendation: an agent-neutral scaffolder with markdown as the only truth

**Positioning.** Position it as a bootstrapper, not a memory engine. One-line pitch: *"Scaffold an LLM wiki for your life and your repos, readable by every agent: AGENTS.md, Agent Skills and plain markdown, no database, no lock-in."* The differentiators to lead with are the four gaps above: vault plus repos under one model, neutral by construction, safe plan-approve-apply with versioned upgrades, and freshness and privacy built in.

**Canonical file layout.** Two scopes share one schema. The home vault holds global memory; each repo holds a lightweight stub that links back to it.

```
~/<vault>/                         # home vault (global scope); open in Obsidian
  AGENTS.md                        # canonical schema/router; <200 lines; critical rules here
  CLAUDE.md                        # generated: "@AGENTS.md" + Claude-only notes (import, not symlink)
  GEMINI.md                        # generated: "@AGENTS.md"
  .aider.conf.yml                  # generated: read: [AGENTS.md]
  index.md                         # catalog, one line per page; agents read first
  log.md                           # append-only episodic log, grep-able prefixes
  hot.md                           # small "currently relevant" set; fights bloat
  inbox/                           # unreviewed ingests (quarantine: untrusted data)
  raw/                             # immutable sources (provenance)
  wiki/                            # semantic memory: entities/ concepts/ decisions/ people/
  projects/<slug>.md               # one page per linked repo, with path + status
  memory/MEMORY.md                 # profile/preferences index + topic files
  .agents/skills/<name>/SKILL.md   # canonical skills (required spec fields only)
  .agents/mcp.json                 # canonical MCP server list -> generated per tool
  .claude/skills/                  # generated copies of .agents/skills
  derived/                         # gitignored, rebuildable: graphify, FTS, embeddings
  .<tool>/manifest.json            # schema version, applied-plan hash, generated-file list
  .gitignore, pre-commit (gitleaks)

<any-repo>/                        # project scope stub
  AGENTS.md                        # repo rules + "Global context: <vault>/projects/<slug>.md"
  CLAUDE.md / GEMINI.md / .aider.conf.yml   # generated bridges as above
  memory/MEMORY.md                 # index; decisions.md, log.md, gotchas.md
  .agents/skills/ -> .claude/skills/        # repo-specific skills, mirrored
  # never emitted: .cursorrules, .windsurfrules, .rules, .github/copilot-instructions.md
```

Use a visible `memory/` folder rather than `.agents/memory/`, because Obsidian hides dot-folders and the human must be able to browse and edit memory. Every memory page carries frontmatter with `type`, `scope` (global/project/session), `as_of`, `last_verified`, `source`, `confidence` and `sensitivity` (with a `never-send` value that the AGENTS.md rules and any MCP adapter honor). Adopt obsidian-second-brain's rule that every fact is timeless, dated or a pointer to a live source, and require a human `keep` step before a lesson becomes a rule in AGENTS.md.

**Role of Obsidian: recommended viewer, never a dependency.** Everything must work with `cat` and `grep` in a headless terminal, because that is the only interface every agent and local-model harness shares. Obsidian contributes wikilinks, frontmatter, graph view and Bases for free, so write Obsidian-flavored markdown and ship kepano's obsidian-skills as a suggested install so agents write valid Obsidian syntax. Do not build an Obsidian plugin in the MVP; Agent SDK plugins are desktop-only anyway ([obsidian-claude-code](https://github.com/Roasbeef/obsidian-claude-code)).

**Role of graphify: optional, derived layer.** Offer `<tool> index --graph` as an opt-in adapter that runs graphify into `derived/graphify/` for code repos and large corpora, gitignored and rebuildable, with `--code-only` as the default so nothing leaves the machine and `GRAPHIFY_QUERY_LOG_DISABLE=1` set. Never let graphify write into `~/.claude/CLAUDE.md` or the canonical wiki, and never treat `graph.json` as memory. Make it optional because its license is unresolved, it has a commercial cloud tier, its savings are near zero on small corpora, and its inferred edges reduce trust in exactly the files the human curates. Treat Basic Memory the same way: an optional runtime MCP server over the vault, run as a separate process to keep its AGPL-3.0 license at arm's length (worth a quick legal check).

**MVP scope.** Ship a single CLI (`npx`/`uvx`) with seven capabilities, aiming to borrow proven ideas rather than invent them:

| Ship in MVP | What it does | Borrowed from |
|---|---|---|
| `init` | Interview, then print a plan with a hash, apply only on approval; vault or repo mode | claudesidian, claude-obsidian |
| `adopt` | Non-destructively wrap an existing vault or repo, never reorganizing notes | claude-obsidian |
| `link` | Register a repo with the vault: create `projects/<slug>.md` and the repo stub | Gap: unaddressed |
| `sync` | Regenerate bridges, skill mirrors and MCP configs from canonical files; emit Ruler/rulesync-compatible output or call them | Ruler, rulesync |
| `lint` | Staleness by `last_verified`, orphans, oversize files, 32 KiB AGENTS.md chain, missing `@AGENTS.md` import, Zed-shadowing files, secrets | Karpathy lint, COG, standards notes |
| `upgrade` | Versioned migrations that preserve user edits via the manifest | claudesidian `/upgrade` |
| 3 skills | `ingest` (inbox to wiki with sources), `consolidate` (dedupe, flag contradictions), `session-close` (append log, update `hot.md`) | LLM Wiki, Letta sleep-time |

Two organization profiles are enough at launch: **LLM Wiki** (the default) and **PARA**, because the 2026 projects show folder taxonomy matters less to agents than an index, consistent frontmatter and typed links.

**What to defer.** Defer your own MCP memory server (document Basic Memory instead), any graph or embedding engine (adapters only), conversational memory capture of the claude-mem kind, an Obsidian plugin or GUI, cloud sync and multi-user access control, session hooks beyond the two or three agents that support them uniformly, additional organization profiles (Johnny Decimal IDs are an interesting untried niche for agent-addressable keys, but not a launch feature), importing from vendor auto-memory silos, and any bet on the W3C or `.mem` memory formats until one is actually adopted.

## Conclusion

The evidence reframes the opportunity. The hard parts people associate with "AI memory" (graphs, embeddings, temporal reasoning) are already well served by funded projects, and the industry is quietly retreating from them toward plain files: Anthropic's memory tool, Letta's MemFS and Karpathy's wiki all land on markdown in a folder. What nobody owns is the boring, high-leverage layer underneath: a correct, safe, upgradeable scaffold that puts the right files in the right places for every agent at once, across a person's whole working life rather than one repo. That is a standards-compliance and lifecycle problem, not an AI problem, which makes it defensible through correctness rather than model quality.

Two implications follow. First, the project's value compounds with each standard it tracks precisely; its lint rules (the Claude import pitfall, Codex's size cap, Zed's shadowing order) are themselves the product, and they will need maintenance as Gemini CLI's move to Antigravity and Windsurf's reported rebrand play out. Second, keeping graphify, Basic Memory and future memory standards as swappable adapters over a markdown core means the tool gets better as the ecosystem improves instead of competing with it. Ship it under its own name, and let MemPalace remain a runtime your users might plug in, not a project they mistake you for.
